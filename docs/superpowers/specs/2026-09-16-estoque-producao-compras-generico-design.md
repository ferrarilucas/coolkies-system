# Estoque, Produção e Lista de Compras — sistema genérico

Data: 2026-09-16
Status: aguardando revisão do usuário
Predecessor: [2026-09-15-mercado-compras-generico-design.md](./2026-09-15-mercado-compras-generico-design.md)
  (generalizou Compras/Insumo, mas deixou explicitamente fora de escopo o
  "rebranding do vocabulário e a unificação Produto/Insumo" — é exatamente
  isso que este spec resolve).

## Objetivo

O Cookies App vai deixar de ser um sistema focado em confeitaria/cookies
para virar um SaaS genérico de estoque + vendas para pequenos negócios de
qualquer ramo (loja de roupas, papelaria, marcenaria, etc.), com múltiplos
workspaces de perfis diferentes. Este spec cobre a generalização de três
módulos interligados: **Estoque** (ex-Despensa), **Produção** e **Lista de
compras**. Fica fora deste spec o catálogo multi-dimensional de variantes
(cor + tamanho simultâneos) — projeto futuro à parte, ver "Fora de escopo".

## Contexto atual (antes desta mudança)

- `Product` (catálogo vendável) e `Ingredient` (matéria-prima) são
  entidades separadas. Um insumo marcado `forResale=true` ganha
  automaticamente um `Product` pareado (`resaleProductId`) só para poder
  ser vendido — um hack de duas tabelas representando o mesmo item físico.
- `Flavor` é a única dimensão de variação de um `Product` (nome do domínio:
  "sabor"), usada tanto no catálogo/venda quanto na distribuição de
  produção (`ProductionFilling`, "recheio").
- Estoque é recalculado **na leitura**, de dois jeitos diferentes:
  estoque de insumo = `Σ PurchaseItem` − (percorre receitas × lotes de
  produção) − `Σ StockMovement(SALE)` para revenda; estoque de produto =
  `Σ ProductionFilling` − `Σ SaleItem`. A tabela `StockMovement` existe
  ("event sourcing", conforme comentário no schema) mas não é a fonte de
  verdade única hoje — só é escrita para compra de insumo de revenda e
  para venda/produção/ajuste de produto acabado.
- Lista de compras (`ShoppingListItem`) só é criada por um botão "Gerar
  lista de compras" que varre insumos abaixo do mínimo e cria/atualiza
  linhas com `autoGenerated=true`. **Não existe nenhuma ação para
  adicionar um item manualmente** — só marcar como comprado
  (`toggleShoppingListItem`), o que apaga o item sem deixar rastro de
  compra.

## Decisões

1. **`Product` e `Ingredient` se fundem em um único modelo `Item`.** Um
   `Item` tem uma unidade base (`G`/`ML`/`UN`, hoje só em `Ingredient`) e
   dois booleanos independentes: `sellable` (aparece no catálogo/preço,
   pode entrar numa venda) e `productionInput` (pode ser usado como
   insumo de uma `Recipe`). Um item pode ter os dois marcados ao mesmo
   tempo — é exatamente o caso hoje coberto pelo hack
   `forResale`+`resaleProductId`, que deixa de existir.
2. **`StockMovement` vira a única fonte de verdade de estoque, para
   qualquer item.** Toda compra, produção (entrada do produzido e saída
   do insumo consumido), venda e ajuste manual grava uma linha. O saldo
   atual de um item+variante é sempre `Σ StockMovement.quantity`. Isso
   substitui as duas lógicas de recálculo na leitura por uma única regra,
   e faz o alerta de estoque mínimo (`minStock`) funcionar igual para
   insumo de produção ou produto acabado.
3. **Novo tipo de movimento `CONSUMPTION`** (negativo) para o insumo
   consumido numa produção — hoje esse consumo é só calculado na leitura
   (`buildConsumptionMap`), nunca vira uma linha de `StockMovement`.
4. **`Flavor` → `Variant`; `ProductionFilling` →
   `ProductionVariantLine`; `RecipeIngredient` → `RecipeItem`.** Mesma
   estrutura e comportamento de hoje (uma dimensão de variação por item),
   só sem vocabulário de comida. `Flavor.fillingRecipeId` (receita de
   recheio por sabor) vira `Variant.recipeId` (receita adicional por
   variante).
5. **Item unificado habilita produção em múltiplos estágios de graça**
   (um item produzido pode futuramente ser insumo de outra receita, já
   que `RecipeItem` referencia `Item` e não mais só `Ingredient`). Não
   desenho UI para isso agora — é uma consequência do modelo, não um
   requisito deste projeto.
6. **Lista de compras vira uma lista livre, não uma geração automática.**
   - CRUD completo e sempre disponível: adicionar (texto livre ou
     vinculado a um `Item` cadastrado, com autocomplete), editar, apagar,
     marcar como comprado — sem depender de nenhum job de geração.
   - Itens abaixo do `minStock` aparecem numa seção separada
     "Sugestões", cada um com um botão explícito "+ Adicionar à lista".
     Substitui o botão "Gerar lista de compras" (que criava tudo de uma
     vez, silenciosamente, misturando automático e manual na mesma
     lista).
   - Marcar como comprado apenas risca o item (ação rápida). Para itens
     vinculados a um `Item`, um botão adicional opcional "Registrar
     compra" abre o formulário de Compra pré-preenchido com esse item.
     Itens de texto livre sem vínculo (ex.: "café de casa") só são
     riscados — não têm com o que se conectar no estoque, e não deveriam
     forçar isso.
   - Campo `autoGenerated` sai do modelo de UI (não existe mais "duas
     listas" na mesma tela).
7. **Insumo/Produto usado em uso pessoal e no negócio ao mesmo tempo**
   (ex.: açúcar do negócio e do café de casa) não ganha modelagem
   especial — é só um `Item` com `minStock` e um `ADJUSTMENT` manual
   cobre correções de saldo quando o consumo real diverge do calculado
   (uso já existente do tipo `ADJUSTMENT`, sem mudança).

## Modelagem de dados

Migração escrita à mão (sem `prisma migrate dev`), aplicada via `docker
psql` nos bancos `cookies` e `cookies_test`, seguindo a prática já usada no
projeto (ver spec predecessor).

### `Item` (substitui `Product` + `Ingredient`)

| Campo             | Tipo                | Papel                                                    |
|--------------------|---------------------|------------------------------------------------------------|
| `id`               | String @id          | preservado do `Product` original (ver algoritmo abaixo)   |
| `name`             | String              | —                                                          |
| `active`           | Boolean             | —                                                          |
| `unit`             | BaseUnit @default(UN) | novo em itens ex-`Product` (sempre eram vendidos em "un") |
| `sellable`         | Boolean @default(true) para ex-`Product`, `false` para ex-`Ingredient` puro | aparece em catálogo/preço/venda |
| `productionInput`  | Boolean             | == `Ingredient.isRawMaterial` (default `true` para ex-`Ingredient`, `false` para ex-`Product` puro) |
| `minStock`         | Float?              | == `Ingredient.minStock`; `null` para ex-`Product` puro    |

**Algoritmo de merge** (preserva o máximo de FKs sem remapear valores):

1. `Product` vira a base física de `Item` (rename de tabela + novas
   colunas `unit`/`sellable`/`productionInput`/`minStock` com defaults
   acima).
2. Para cada `Ingredient` com `forResale=true AND resaleProductId != null`
   (já existe um `Item` pareado, criado pelo hack atual): copia
   `unit=baseUnit`, `productionInput=isRawMaterial`, `minStock=minStock`
   para a linha de `Item` de id `resaleProductId`; repointa
   `purchase_item.ingredient_id`, `recipe_ingredient.ingredient_id` e
   `shopping_list_item.ingredient_id` desse insumo para
   `item_id = resaleProductId`; apaga a linha de `Ingredient`.
3. Para cada `Ingredient` restante (matéria-prima pura, sem `Product`
   pareado): `INSERT INTO item` usando **o mesmo `id`** do `Ingredient`
   (assim as colunas `*_ingredient_id` podem só ser renomeadas para
   `*_item_id` em seguida, sem precisar remapear valor nenhum).
4. Renomeia colunas: `purchase_item.ingredient_id` → `item_id`,
   `recipe_ingredient.ingredient_id` → `item_id` (tabela renomeada para
   `recipe_item`), `shopping_list_item.ingredient_id` → `item_id`,
   `sale_item.product_id` → `item_id`, `price_list_item.product_id` →
   `item_id`, `stock_movement.product_id` → `item_id`,
   `production_batch.product_id` → `item_id`, `flavor.product_id` →
   `item_id` (tabela renomeada para `variant`).
5. Dropa a tabela `Ingredient` (já vazia).

Nenhum histórico de venda, compra ou produção perde referência — todo
remap é de coluna/tabela, não de valor de FK, exceto o repoint pontual do
passo 2 (que troca `ingredientId` por `resaleProductId`, ambos já
existentes).

### `StockMovementType`

Adiciona o valor `CONSUMPTION` (`ALTER TYPE ... ADD VALUE`).

### Renomeações simples (sem mudança de estrutura)

- `Flavor` → `Variant` (tabela e todas as FKs `flavorId` → `variantId`)
- `ProductionFilling` → `ProductionVariantLine`
- `RecipeIngredient` → `RecipeItem` (já coberto no passo 4 acima)

## Fluxo de UI

**Estoque** (`/stock`, ex-`/pantry`): tela única mostrando saldo atual de
todo `Item` (insumo, produto acabado ou os dois), somando
`StockMovement` — substitui as duas visões desconectadas de hoje
(despensa de insumos em `/pantry` e estoque de cookies só visível em
`/products`).

**Cadastro de item** (`/admin/catalog` + `/admin/ingredients`
continuam como duas entradas de navegação, mas passam a ser visões
filtradas do mesmo `Item`: "Catálogo" = `sellable=true`, "Insumos" =
`productionInput=true`. Um item marcado com os dois aparece nas duas
listas.  Escolhido para não forçar uma reestruturação de navegação junto
com a unificação de dados — pode ser revisitado depois.

**Produção**: `ProductionForm` troca "Produto"/"sabor" por
"Item"/"variante" na UI; ao salvar, além do `ProductionBatch`, grava
`StockMovement(PRODUCTION, +qty)` por item/variante produzido e
`StockMovement(CONSUMPTION, -qty)` por insumo de receita consumido
(calculado uma vez na gravação, não mais recalculado toda leitura).

**Compras**: `PurchaseItem` referencia `Item`; toda compra grava
`StockMovement(PURCHASE, +qty)` para o item comprado — deixa de ser um
caso especial só de insumo de revenda (natural, já que "insumo de
revenda" não existe mais como conceito separado).

**Lista de compras** (`/stock/shopping-list`, ex-`/pantry/shopping-list`):
- Formulário de adicionar item (texto livre ou combobox de `Item`
  cadastrado, quantidade/unidade opcional).
- Seção "Sugestões": itens com `belowMin`, botão "+ Adicionar à lista"
  por item (opt-in, não mais automático).
- Cada linha: switch "comprado" (marca `done`, comportamento atual) +
  botão opcional "Registrar compra" quando a linha tem `itemId` (abre
  `PurchaseDialog` pré-preenchido com esse item).

## Impacto no custo/lucro (dashboard)

Sem mudança de comportamento: a lógica de dois caminhos de COGS
introduzida no spec anterior (custo de item vendido = última compra
direta, se aplicável, senão custo de produção via receita) continua
igual, só trocando as referências de `Product`/`Ingredient` para `Item`
unificado — o `if (product.id === ingredient.resaleProductId)` vira
simplesmente checar se aquele `Item` tem `StockMovement(PURCHASE)`
diretos.

## Testes

Suites existentes que hoje testam Ingredient/Product/Flavor
separadamente (`ingredients.test.ts`, `production*.test.ts`,
`purchases.test.ts`, `shopping-list.test.ts`, `dashboard*.test.ts`)
precisam ser reescritas para o modelo `Item` único — cobrindo em
particular: item com `sellable` e `productionInput` juntos (caso
substituindo o antigo "insumo de revenda"), saldo calculado 100% via
`StockMovement` (incluindo `CONSUMPTION` gerado na produção), e o novo
fluxo de lista de compras (adicionar manual, sugestão opt-in, registrar
compra a partir de um item da lista).

## Fora de escopo (explícito)

- Catálogo com variantes multi-dimensão (cor + tamanho simultâneos) —
  projeto futuro à parte, com seu próprio spec.
- Mudança de metodologia de custeio (continua "última compra").
- Unificar as telas de cadastro `/admin/catalog` e `/admin/ingredients`
  numa única tela de "Itens" — mantidas como duas visões filtradas por
  ora.
- UI para produção em múltiplos estágios (item produzido virando insumo
  de outra receita) — o modelo permite, mas não é construído agora.
